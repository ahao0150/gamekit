# Canvas 2D 性能基准（T26）

> 回答一个问题：**Canvas 2D 到底能画多少，什么时候必须上 WebGL。**
>
> 基准代码在 [`games/bench/`](../games/bench/)，本文所有数字都是
> 无头 Chrome 真跑出来的，不是估算。重跑命令见文末「复现」。

---

## 一、结论

### 1.1 低端机（6× 降频）16.7ms 预算内能画多少

按「稳 60fps」（帧间隔 ≈ 16.7ms，不是只看 draw 耗时）算：

| 负载 | 稳 60fps 的上限 | 超了会怎样 | 依据（N=上限 / 上限以上） |
|---|---|---|---|
| 精灵 `drawImage` 64×64 | **≈ 500 个** | 1000 个 → 40fps | 500：帧间隔 16.7ms；1000：25ms（draw p95 仍只有 15.5ms） |
| 文字 `fillText` 14px | **≈ 200 个** | 500 个 → 30fps | 200：16.7ms；500：33ms |
| UI 块 `fillRect` 64×32 | **≥ 1000 个** | 实测 1000 个仍稳 | 1000：draw 1.3ms、帧间隔 16.7ms |
| 发光 `drawWithGlow`（3 层径向） | **≈ 20 个** | 30 个起 p95 掉到 50ms，50 个 → 30fps | 20：帧间隔 16.7ms；30：p95 50ms；200：133ms（12fps） |

同一组数字在**软件光栅（GPU 极弱，SwiftShader）**下会进一步下降：精灵约 200–300、
文字约 500、发光约 20（N=20 的 p95 已经 33ms）。
也就是说「低端安卓」的真实区间是：**精灵 200–500、文字 200–500、UI 块 1000+、发光 20**。

### 1.2 不要为 WebGL 重写渲染层

三条理由，都是数据支撑的：

1. **主流玩法的量级远不到上限。** 6× 下 500 个精灵、200 个文字、1000 个 UI 块都能稳 60fps。
   一个 2D 小游戏同屏通常 50–200 个精灵、几十个文字，离上限有 2–10 倍余量。
2. **瓶颈不在「绘制调用次数」，在填充率。** 1× 下画 1000 个精灵只要 1.0ms（稳 60fps），
   画 1000 个 glow 要 6.7ms 且 500 个就开始掉帧——**单元素成本是精灵的 6–8 倍**，
   因为每个 glow 要画 3 层半透明径向渐变、覆盖面积还带光晕外扩。
   **WebGL 也受同一套填充率限制**，换渲染后端并不会让 glow 变便宜。
3. **WebGL 的收益只在「上千精灵/密集粒子」这个区间。** 如果将来真做弹幕/粒子海，
   先用「降数量 + 分帧 + 预烘焙」顶，顶不住再评估 WebGL——那时应该重新跑本基准，而不是现在提前重写。

### 1.3 真正该做的优化（按 ROI 排序）

1. **静态 UI 层离屏缓存**：6× 下 200 个 UI 元素每帧重画 5.50ms → 缓存后 0.20ms，
   **省 5.3ms（96%）**，而且缓存版的帧间隔全程 16.7ms。这就是 `.ui` 的 base 层该有的做法。
2. **光晕改预烘焙贴图**：`drawWithGlow` 每帧 `createRadialGradient` × 3 是纯浪费——
   同一形状的光晕可以预渲染成一张 128×128 贴图，之后每帧一次 `drawImage`。
   本次数据里 glow 是**唯一**在 6× 下 N=50 就掉帧的负载，改这一个点收益最大。
3. **同屏特效预算**：低端机同屏 glow 类元素**不超过 20 个**（30 个开始 p95 掉帧）；
   超过就降层数（`layers: 3 → 2`）或改贴图。

## 二、怎么测的

### 2.1 环境

| 项 | 值 |
|---|---|
| 浏览器 | HeadlessChrome/155.0.0.0（无头，Windows） |
| 渲染后端（硬件组） | `ANGLE (NVIDIA, NVIDIA GeForce RTX 3060, Direct3D11 vs_5_0)` |
| 渲染后端（软件组） | `ANGLE (Google, Vulkan 1.3.0 SwiftShader Device (Subzero))` |
| 画布 | 390×844 逻辑像素，dpr=1（dpr=2 单列一组，见 3.7） |
| 降频 | CDP `Emulation.setCPUThrottlingRate`：1× / 4× / 6×（6× ≈ 低端机 CPU） |
| 采样 | 每配置预热 15 帧（丢弃）+ 采样 120 帧（部分补测 60–80 帧，表中已注明） |

### 2.2 负载

| kind | 内容 |
|---|---|
| `sprite` | N 次 `drawImage`，64×64，从一张 512×512 图集取（每格有圆 + 斜线图案，不是纯色块） |
| `text` | N 次 `fillText`，14px 中英混排（「包裹已送达 · +12 积分」「Score +42」…） |
| `rect` | N 次 `fillRect`，64×32，`rgba(120,180,255,0.35)` |
| `glow` | N 个 `drawWithGlow` 包裹的 64×64 方块，3 层径向渐变——**用的是 `packages/runtime/src/core/fx/glow.ts` 真实现**，不是复制品 |
| `ui-direct` | 静态 UI 层（面板 + 图标 + 文字，每元素 3 次绘制）每帧全部重画 |
| `ui-cached` | 同一份 UI 层预先画到离屏 canvas，每帧只 `drawImage` 一次 |

坐标在创建场景时**预计算**（互质步长 97/131 平铺），`draw` 里只有绘制调用——
否则测出来的是「随机数 + 取模 + 绘制」，不是绘制成本。

### 2.3 三个指标，为什么都要看

| 指标 | 测什么 | 局限 |
|---|---|---|
| `draw`（中位数 / p95） | `performance.now()` 包住 `clearRect` + 场景绘制 | **只测 JS 提交，测不到 GPU 光栅与合成** |
| `interval`（中位数 / p95） | 相邻两次 `requestAnimationFrame` 时间戳差 | 是真实帧率证据，但无法拆分「光栅 / 合成 / 调度」各占多少 |
| `flush` | 每帧末尾 `getImageData(0,0,1,1)` 强制同步 | 只抓到命令缓冲级同步，**抓不到合成器成本**（见 3.9） |

**本文的结论以 `interval` 为准。** 本次实测就抓到了只看 `draw` 会得出错误结论的例子：
6× 下画 1000 个精灵，`draw` 的 p95 只有 15.5ms（看起来「刚好在 16.7ms 内」），
但**帧间隔是 25ms**——JS 提交完了，GPU/合成没跟上，实际 40fps。

### 3.6 离屏缓存对照：静态 UI 层

同一份 UI 层（面板 + 图标 + 文字）：每帧全部重画 vs 预画到离屏 canvas、每帧一次 `drawImage`。

| 降频 | N=20 | N=50 | N=100 | N=200 |
|---|---|---|---|---|
| 1× | 0.20 → 0.00（省 0.20） | 0.30 → 0.00（省 0.30） | 0.50 → 0.00（省 0.50） | 0.70 → 0.00（省 0.70） |
| 4× | 0.70 → 0.20（省 0.50） | 1.20 → 0.20（省 1.00） | 1.90 → 0.10（省 1.80） | 3.30 → 0.20（省 3.10） |
| 6× | 1.20 → 0.30（省 0.90） | 2.00 → 0.30（省 1.70） | 3.00 → 0.20（省 2.80） | 5.50 → 0.20（省 5.30） |

数字 = 每帧重画的中位数 → 缓存后一次 `drawImage` 的中位数（括号里是差值）。
缓存后不论 N 多大都是 0.2–0.3ms（一次全屏贴图），6× 下 200 个元素省掉 5.3ms ≈ 一帧预算的 32%。
且缓存版帧间隔全程 16.7ms。**结论：值。**

**T30 已把这个结论落地成引擎能力**：`packages/runtime/src/core/render/cache.ts` 的
`createLayerCache`（平台侧新增可选成员 `PlatformAdapter.createCanvas`，web/wx/tt/mock 四端实现）。
在真 Chrome 里用引擎实现复测（6× 降频、200 个 UI 元素、120 帧）：

| 画法 | draw 中位数 / p95 | 帧间隔 |
|---|---|---|
| 每帧重画 | 5.90–7.20 / 8.40 ms | 16.70 / 16.80 |
| 手写离屏 canvas | 0.40 / 0.60 ms | 16.70 / 16.80 |
| 引擎 `createLayerCache` | 0.40 / 0.70 ms | 16.70 / 16.80 |

引擎实现与手写离屏**完全一致**（没有额外抽象开销），比每帧重画省 **93–96%**。
（两次测量 5.90 / 7.20 的差异来自机器上同时跑着多个 dev server，属正常波动。）

### 3.9 flush 对照：为什么它不能当主指标

| 配置 | 普通（提交） | flush（强制同步） | 真实帧间隔 |
|---|---|---|---|
| 精灵 N=500 | 0.50 / 0.80 | 1.10 / 1.60 | 16.70 / 16.80 |
| 精灵 N=1000 | 1.00 / 1.50 | 1.00 / 2.00 | 16.70 / 16.80 |
| 发光 N=500 | 4.05 / 6.60 | 4.25 / 5.70 | 33.30 / 33.40 |
| 发光 N=1000 | 6.70 / 10.50 | 8.15 / 11.70 | 50.00 / 66.70 |

`getImageData(0,0,1,1)` 强制同步只比普通提交多 0.2–1.5ms，**没有**反映出 50ms 的真实帧间隔。
说明这个手段只能等到命令缓冲排空，等不到合成器出帧。诚实结论：flush 用来确认
「命令提交本身确实不慢」有效，用来测总帧成本无效——只有 rAF 帧间隔能测到全貌。

## 四、局限（读结论前必须知道）

1. **CDP 降频只降 CPU，不降 GPU。** 6× 模拟的是「CPU 弱」，不是「整机弱」。
   填充率类负载（glow）在真实低端机上会更差，因为它们的 GPU 也弱。为此补了 3.8 的软件光栅组作下界。
2. **本机 GPU 是 RTX 3060 独显**，比任何低端安卓强一个数量级以上。所以 3.1–3.5 是**乐观上限**，
   真实低端机取 3.8 那组（软件光栅）更接近。
3. **无头 Chrome 与真机浏览器存在差异**：合成路径、vsync、电源策略都可能不同。
   本基准比的是「相对成本与量级」，不是真机绝对帧率。
4. **测量有方差，尤其 glow。** 1× glow N=500 跑了三次：draw 中位数 6.75 / 4.00 / 4.05，
   帧间隔 50.0 / 16.7 / 33.3。draw 稳定在 4.0ms，但帧间隔在 16.7–50 之间跳——
   这个配置正好在 60fps 的临界点，**结论应表述为「临界掉帧」而不是某个确定帧率**。
   表中 glow 的 1× 行用重跑值。
5. **采样帧数**：主矩阵 120 帧，补测（flush / dpr2 / 软件光栅 / glow 小 N）为 60–80 帧，不影响量级判断。

```bash
cd games/bench          # 从仓库根出发（仓库根 = gamekit/）

# 手动开页面（1×）
node ../../node_modules/vite/bin/vite.js --port 5300

# 全矩阵：1×/4×/6× × 4 负载 × N=50..1000（约 6–8 分钟）
node tools/run-bench.mjs

# 软件光栅下界
node tools/run-bench.mjs --software --rates 1,6 --kinds sprite,text,glow --ns 200,500,1000

# 高分屏
node tools/run-bench.mjs --dpr 2 --rates 1,6 --kinds sprite,text --ns 500,1000

# 原始数据落盘
node tools/run-bench.mjs --out out/matrix.json
```

脚本自己起 Vite、自己开无头 Chrome、`finally` 里自己关（不残留进程）。stdout 是 markdown，
进度在 stderr。更多参数见 [`games/bench/README.md`](../games/bench/README.md)。
