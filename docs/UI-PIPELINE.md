# UI 生产管线（完整图 → 部件 → 位图字体）

> 定稿 2026-10-24。路线由用户在流程图上选定：
> **先出风格板 → 再出整屏 → AI 逆向写 tokens → SAM 按语义层切 → AI inpaint 补 → 位图字体**，
> 并追加一条硬要求：**界面背景必须单独提取成一层**。
>
> 读者：接 UI 素材的 AI / Bot。目标：**一张整图进去，一套能上线的数字资产出来**。

## 0. 这份文档解决什么

团队做游戏 UI 踩过的坑高度重复：图好看但切不出来、切出来一拉伸就变形、
深底时代看不出的错位换浅底才暴露、素材进了包却没有落点、缺图时画面塌成空白。
下面把「怎么出图、怎么切、怎么接、怎么验」固定成流程，每步带验收标准和已知坑。

**一句话原则**：AI 出材质与质感，程序画网格与结构。凡是「必须精确到像素」的东西
（10×10 棋盘、进度条填充、文字基线），都不交给生图模型。

## 1. 管线总览

| 步 | 做什么 | 谁做 | 产出 |
|---|---|---|---|
| ① | 先出风格板（锁画风） | AI / AI | 风格板 PNG（**不进包**） |
| ② | 按风格板出整屏完整界面图 | AI | `full-ui.png`（**不进包**，仅作切图源） |
| ③ | 从整图逆向抽设计语言 | AI | tokens：色值 / 圆角 / 描边 / 字号 / 间距 |
| ④ | SAM 按语义层切割 | AI | 各部件 PNG（真透明） |
| ⑤ | 切开后补全被挡住的部分 | AI（inpaint） | 补齐的部件图 |
| ⑥ | **背景层单独提取** | AI | `bg_*.png` → webp |
| ⑦ | 按界面元素出位图字体 | AI | 字形 atlas + 度量表 |
| ⑧ | 接入代码并按契约验收 | AI / AI | 进包的 `assets/` + `ART_KEYS` |

风格板与整屏图**永远留在 `artifacts/`**，不进 `assets/`（进 `assets/` 就会进包，
实测一次 3.86MB 样张让微信主包到了 3922.9KB，直接顶穿 4MB 红线）。

## 2. 逐步做法

### ① 先出风格板（不直接出整屏）

**为什么**：直接出整屏时，模型会自由发挥——同一款游戏的三张图能出三种画风。
风格板先把「材质、光照、线条语言、色系」定死，整屏只是往这个模子里填内容。

- 产出：1 张风格板（色板 + 2~3 个代表性物件），标注主色/辅色/描边色
- 验收：**整体看**——像同一个世界的吗？退一步看，还能分清主次吗？
- 坑：不要用一组精确色值卡模型。美术没有标准答案，
  「画风一致」是硬标准，「色值差 3 级」不是

### ② 出整屏完整界面图

- 尺寸：按目标机型出（如 768×1680 = 390×844 @2x），**一张到底，不要拼接**
- 内容：真实内容，不是线框——要用真实文字、真实数字、真实按钮文案
- 验收三条（缺一不可）：
  1. 画风与风格板一致（同一套材质/光照/线条）
  2. 颜色一眼可辨：功能不同的元素（主按钮/次按钮/禁用）必须一眼分得开
  3. 每个元素的边界清楚到能被 SAM 切开
- 坑：模型爱把多个元素画成一体（按钮和底板糊在一起），切的时候会连体。
  出图 prompt 里就必须写「元素之间留清楚的分界」

### ③ 逆向抽设计语言（tokens）

AI 从整图里写出代码能用的 tokens，不是写一段描述。

必须落成具体值：

```
主色 / 次色 / 禁用色 / 危险色 / 文字色 / 次文字色
圆角半径（面板 / 按钮 / 输入框各一档）
描边宽度（1px / 1.5px / 2px 各用在什么上）
字号阶（标题 / 正文 / 说明 / 数字）
间距阶（4 / 8 / 12 / 16 / 24）
```

**验收：每个 token 都要能算出对比度。**

| 组合 | 下限 | 实测参考 |
|---|---|---|
| 正文 on 底 | 4.5:1 | 深墨 on 磨砂白 = 15.2:1 |
| 白字 on 主按钮 | 4.5:1 | 白 on `#2E6C60` = 5.87:1 |
| 危险文字 on 底 | 4.5:1 | `#A8412F` on 浅底 = 5.53:1 |
| 图形轮廓 on 底 | 3:1 | 珠子描边 on 浅薄荷 = 4.02–7.33:1 |

- 坑：**模型会把深底配色当默认**。深底上白字是常态，换浅底时所有 `tone=light`
  的文字会直接消失。抽 tokens 时必须同时给出「底是深是浅」。
- 坑：珠色/图标这类「主体色」经常达不到 3:1（实测黄色主体 on 浅薄荷只有 1.30:1）。
  解法是**给主体加 1px 内描边**（描边色 = 0.5×主体色 + 0.5×深墨），描边达标即可，
  不必改主体色相。

### ④ SAM 按语义层切割

按**用途**切，不按视觉块切。标准语义层：

1. `ui/panel` — 通用面板/对话框底板（要能拉伸）
2. `ui/hud-bar` — 顶部横幅（固定尺寸，不拉伸）
3. `ui/btn-<tone>_<state>` — 按钮：primary/secondary × normal/disabled
4. `icons/<name>` — 图标（时钟、温度计、镊子……）
5. `beads/*` 或游戏专属小件 — 有固定尺寸的小元素

- **每个切出来的部件都要有明确落点**。没落点的不切、不进包（死资源坑过一次）。
- 切割后逐个检查：四角真透明（`alpha=0`）、尺寸统一、单张 ≤200KB。
- 坑：SAM 常把「按钮 + 它的阴影 + 底板」切成一块。阴影要么单独切，
  要么在代码里用 `shadowBlur` 画，别指望一张图带阴影还能拉伸。

### ⑤ 补全被挡住的部分（inpaint）

切开之后的典型残缺：

- 面板挡住的那块背景 → 补
- 按钮压住的面板圆角 → 补（否则按钮挪位置就露缺口）
- 被裁掉一半的装饰边 → 补

**验收**：补完的图与原图在「未被遮挡区域」逐像素一致；只看补区是否自然。

- 坑：inpaint 会补出「AI 味」的随机细节，同一张图重跑两次结果不同。
  补完立刻冻结，别反复重跑。
- 替代方案（更可控）：**边缘扩展**（把边缘像素向外延 N px）或**纯色/渐变填充**，
  这些是确定性算法，不会飘。

### ⑥ 背景层单独提取（用户追加的硬要求）

背景不是「整屏图底下那块」，是**独立一层**：

1. SAM 时把背景（含最远层的装饰）单独切出来，不与任何 UI 元素合并
2. UI 挡住的部分按 ⑤ 补全，补成一张**完整可铺满**的背景
3. 输出按 `cover` 绘制设计：宽高比覆盖目标机型，短边溢出裁掉
4. 体积：转 webp，目标 ≤180KB

**webp 质量不要盲选 q82。** 素材主体如果是 AI 颗粒噪点，低 q 会把渐变压成台阶：

| 编码 | 体积 | 雾紫区最长平坦段 |
|---|---|---|
| 原始 PNG | 2023 KB | 1 行 |
| q82 | 8.6 KB | **23 行**（明显 DCT 块） |
| q95 | 34.0 KB | 10 行 |
| **q98** | **74.3 KB** | **3 行**（肉眼与原始一致） |
| q100 | 83.9 KB | 8 行（**反而更差**，量化非单调） |

判据：按真实渲染路径缩放到目标尺寸，把对比度拉到极限，看有没有块状。
真实观感下无差别的，不要为了体积往低 q 走。

- 坑：背景里**不要画 UI**（按钮、文字、图标）。背景一改，所有 UI 都要重画。
- 坑：小游戏端 webp 兼容性要单独验；备选 JPEG q90（体积大 11KB 左右）。

### ⑦ 位图字体

只给**装饰性/固定内容**做位图字体：数字（分数、倒计时）、固定文案（关卡名、按钮字）。

- 字形集：`0-9`、`:`、以及本项目用到的固定汉字
- 每个字形尺寸统一、**基线对齐**、留白一致
- 小字号验收：**320 宽屏**下等比例缩放后仍可辨认（6px 级别）
- 输出：字形 atlas（一张 PNG）+ 度量表（每个字形的 x/y/w/h + advance）

**动态文字不要做位图字体**：玩家名、随机文案、可变长度的说明，用 canvas 文字渲染。
位图字体只解决「固定字形 + 统一风格」这一件事。

## 2.5 SAM 实测记录（2026-10-24，拼豆工坊 mockup）

环境：ComfyUI 0.41.3 + Impact-Pack（`SAMLoader` / `SAMDetectorCombined`），
权重 `sam_vit_b_01ec64.pth`（357.7 MB），RTX 3060 12GB。
输入：`direction-b-acrylic-workshop.png`（768×1680 整屏 UI）。

### 自动模式（`SamAutomaticMaskGenerator`）——对 UI 图不可用

| 指标 | 实测 |
|---|---|
| mask 数量 | 342 |
| 耗时 | 14.7 s（含模型加载 4.4 s） |
| 面积分布（前 48 大） | `>5%` 只有 2 个，`<1%` **46 个** |

切出来的全是色块与条带，不是语义元素：

- 顶部切成一个盖住「标题 + HUD」的大块，不是两个元素
- 10×10 珠子阵列**完全没分开**，被当成一片纹理
- 散落的小 mask 对应的是孤立装饰，不是按钮/图标

**原因**：AI 生成的整屏图元素之间是渐变过渡、没有硬边，SAM 靠边缘分割，
切不开「同一色系的相邻元素」；重复纹理（珠子阵列）会被合并成一片。

### 框提示模式（`SamPredictor.predict(box=)`）——可用，但必须裁到框内

| 区域 | score | fill（mask 面积 / 框面积） | 评价 |
|---|---|---|---|
| 顶部 HUD | 0.982 | 88.5% | 形状准，**溢出框** |
| 主面板 | 0.967 | **104.1%** | 溢出，且把面板里的珠子一起吞了 |
| 底部条 | 0.974 | 89.2% | 准，溢出 |
| 左侧装饰条 | 0.758 | 25.7% | 只切到一部分 |
| 右侧装饰条 | 0.892 | 39.7% | 一般 |
| 单颗珠子（40×40 框） | 0.847 | **128.1%** | 严重溢出，切不准 |

### 由此定下的切层做法

1. **bbox 由设计坐标给，不靠 SAM 发现元素** —— 元素位置是我们自己定的，
   手工框比任何检测器都准（也省掉 50 MB 的 YOLO 依赖）
2. **SAM 只负责「框内抠形状」** —— 它的价值是给出带圆角的真实轮廓、去掉背景，
   不是找元素
3. **输出必须 `mask &= box`** —— 实测溢出 4%~28%，不裁就会把旁边的背景带进部件
4. **重复小件（珠子、格子）不要走 SAM** —— 按设计坐标程序化切，或直接程序生成
5. **出图阶段就必须保证元素硬边界** —— 这是 SAM 能切开的前提；
   软边、同色渐变的图，后面哪一步都救不回来

### 第二轮：硬边界重出图 + 结论修正

按硬边界要求重出了一张 `full-ui-v2.png`（768×1680，三分区明确：
HUD 0–114 / 面板 114–1588 / 底栏 1588–1680，分界两侧均值差 33.6 与 173.1）。
再切一遍，结论要修正：

| 区域 | 框怎么给 | score | fill_clip | overflow | 四角透明 |
|---|---|---|---|---|---|
| 顶部 HUD | 目测 | 0.998 | **100.0%** | 7.7% | — |
| 主面板 | 目测 | 1.007 | **99.8%** | 0.8% | — |
| 底部条 | 目测 | 0.975 | **100.0%** | 12.4% | — |
| 左胶囊 | 目测 | 0.924 | 66.3% | **47.3%** | — |
| 左胶囊 | **像素分析自动定位** | 0.975 | 69.7% | **2.2%** | **4/4** |
| 右胶囊 | **像素分析自动定位** | 0.997 | 90.0% | **0.0%** | **4/4** |

三条修正：

1. **矩形元素（HUD / 面板 / 底栏）：`fill_clip = 100%`，SAM 输出就是整个框** ——
   等价于「直接按框裁」，SAM 在这类元素上不提供增量信息。**不要为它们跑 SAM**。
2. **框给准了 SAM 才有效**：目测框溢出 47%，用 20 行像素分析自动定位后溢出降到 0–2.2%，
   四角透明 4/4，score 0.997。**框可以自动得到，不需要 YOLO**。
3. **但 SAM 给的圆角是错的**：放大 6 倍看，它给的是「桶形」（上下平、左右外凸），
   不是胶囊（左右两端半圆）。**圆角/胶囊素材不要用 SAM 抠形状** ——
   按规格程序绘制（`drawCapsule` 三段切）或直接出成品尺寸。

还有一条能力边界要记住：**AI 出整屏图搞不定精确网格**。这张 v2 的珠子阵列被画成
约 14 列 × 20 行、格子大小不一、行列不对齐、外圈还有褪色方块 ——
prompt 再改也解决不了。**网格类结构一律程序画，AI 只出材质**。

产物：`games/pindou-workshop/artifacts/ui-pipeline/sam-test/`（第一轮）、
`sam-test-v2/`（第二轮）、`full-ui-v2/`（重出的整屏图与边界证据 `edge-proof.png`）。

## 3. 九宫格与胶囊的数学约束（必读，直接决定素材规格）

这一节是硬约束，不遵守切出来的图一定变形。

**九宫格的 border 会按「目标尺寸 / 源尺寸」比例缩放**（`bx = border × dw / sw`）。

实测：240×240 的源面板拉到 780×152 时，`bx = 195 / by = 38`，
源图 60×60 的角被拉成 195×38 —— 圆角变扁弧。

**结论：一张方图不可能同时满足 5:1 横幅与整屏两种比例都零变形。**
所以必须拆：

| 用途 | 素材规格 | 切法 |
|---|---|---|
| 顶部横幅 / HUD 条 | 780×152（按目标 2x 出） | **固定尺寸直绘，不拉伸** |
| 通用面板 / 对话框 | 240×240 | 九宫格，border 取实测圆角外沿 |
| 胶囊按钮 | 336×126，cap=63 | **三段横切**（左帽 / 中段 / 右帽） |

胶囊为什么不能用九宫格：源图高 126、左帽 63，`sh <= border × 2` 恰好成立，
九宫格会直接拒绝（纵向没有可切片空间）。三段切是这张图的正确切法。

**素材内部必须是均匀色或极缓渐变。** 中心区若有 2~3 级的同心色环，
九宫格拉伸后会在面板中间显出一块「浅灰方块」（实测过：243/244/245/255 四个色环，
拉伸后用户直接报「有个灰块」）。要保留高光就只保留 1~2px 边线，中间一律抹平。

**圆角半径要知道上限**：条高 152 的高光条，半径超过 76 会被钳到 76（变成完全圆头）。
想要「大圆角矩形」而不是「胶囊」时，半径要收到 48 附近，且实测顶部直线段占比：

| 半径 | 顶部直线段 | 占比 |
|---|---|---|
| 24 | 731px | 94% |
| 48 | 683px | 88% |
| 76（半圆头） | 628px | 80% |

## 4. 接入契约（gamekit）

素材进包之前必须过这几关，缺一不可：

1. **登记 `ART_KEYS`**：`src/app/assets.ts` 的清单是本工程「真要用」的素材白名单，
   不在清单里的图不许进 `assets/`
2. **图集**：`game.config.json` 的 atlas 段；单帧别超过图集最大边
3. **缺图回落**：渲染层必须每帧 `get(key)`，拿不到就走纯色/直角的等价物，
   **不能是空白或布局塌陷**。验收方式：跑一遍「图集 404」的环境，布局与颜色必须一致
4. **绘制路径要对**：
   - 九宫格底 → `drawNineSlice`
   - 胶囊按钮 → `drawCapsule`（尺寸必须等于 `DEFAULT_CAPSULE {336,126}`，否则回落）
   - 通用 `button` 组件默认找 `ui/button_normal` / `ui/button_pressed` /
     `ui/button_disabled`，**不是** `ui/btn-primary_normal`。要它吃胶囊素材，
     得给它 `image` prop 或复用 `primaryButton` 的 def 注册新名字
5. **落点断言**：测试要钉「素材真的被画到 canvas」——断言 `drawImage` 调用次数
   （胶囊恰好 3 次、`fillRect` 0 次），不能只断言清单里有这个 key

包体预算：单款小游戏按 **4MB 红线** 留余量，实测控制线 350KB（web）/ 400KB（小游戏）。
背景 ≤180KB、图集 ≤100KB。

## 5. 验收清单（逐条打勾）

出图阶段：

- [ ] 风格板与整屏是同一种画风
- [ ] 功能不同的元素颜色一眼可辨
- [ ] 元素之间有清楚分界，SAM 能切开

切图阶段：

- [ ] 每个部件四角 `alpha=0`（真透明，不是白底/黑底）
- [ ] 同一组部件尺寸统一（按钮都是 336×126、图标都是 96×96）
- [ ] 单张 ≤200KB
- [ ] 中心区均匀，没有 2 级以上同心色环
- [ ] 每张图都有明确落点，没有死资源

接入阶段：

- [ ] tokens 里每对「文字/底」都算过对比度，正文 ≥4.5:1、图形 ≥3:1
- [ ] 缺图跑一遍：布局与颜色与有图时一致（回落是等价物，不是空白）
- [ ] 图集帧数与 `ART_KEYS` 完全一致
- [ ] 绘制路径断言通过（胶囊 3 次 `drawImage` / 0 次 `fillRect`）
- [ ] 三端构建通过，包体在预算内
- [ ] 视觉验收：**看过截图**，说明看到什么，不许用状态断言冒充满意

## 6. 现在这套管线已知的边界

- SAM 切出来的层不能直接当九宫格用，还得按 §3 重新算 border
- inpaint 结果不可复现，补完立刻冻结
- 位图字体只覆盖固定字形，动态文字仍走 canvas 文字
- 背景 webp 在小游戏端的兼容性要单独验
- 一张整图能撑一个界面；多界面（首页 / 盘面 / 结算）要么共用一套部件，
  要么按界面各出一张整页图再切——后者成本线性增长，要在策划阶段就定
